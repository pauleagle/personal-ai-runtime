# Preflight Protocol

## 目的

Preflight Protocol 是所有 AI agent 在開始執行任務前必須完成的起手檢查。

它的目的不是產出結果，而是先降低誤解、錯誤假設、過度修改與任務偏航的風險。

## 核心原則

在開始實作、修改檔案、產生文件或執行命令之前，agent 必須先說明：

1. 對任務的理解
2. 已知的輸入與限制
3. 做出的假設
4. 不確定的地方
5. 是否存在兩種以上可能解讀
6. 可能的風險
7. 預計採取的處理策略
8. 是否需要使用工具、讀檔或修改檔案

## 標準 Prompt

開始前，先列出你對任務的理解、你做了哪些假設、你不確定的地方，以及可能有兩種以上解讀的地方。不要直接產出。

## 適用時機

- 任務需求不夠明確
- 可能會修改多個檔案
- 可能影響架構、命名、資料格式或版本規則
- 需要 agent 自行判斷方案
- 使用者要求「幫我重構」、「幫我整理」、「幫我設計」、「幫我產生規範」
- 發版、tag、README、CHANGELOG、CONTRIBUTING 等文件維護前
- 跨專案變更或可能影響既有行為、公開 API、使用者可見行為

## 不適用時機

- 單純翻譯
- 單純改一句文字
- 使用者已明確指定完整輸出格式
- 任務風險極低且不涉及檔案修改
- 單純事實回答或一行說明

## Agent 行為規則

agent 不應直接開始修改檔案、執行破壞性命令、做出架構決策或開始實作。

除非使用者明確授權，否則應先輸出：

1. Task Understanding
2. Known Inputs / Constraints
3. Assumptions
4. Unknowns
5. Ambiguities
6. Risks
7. Proposed Plan
8. Files likely to be touched

輸出 preflight 前，可以視需要先讀取或搜尋檔案以理解任務，但這個探索階段應保持唯讀。

preflight 應保持精簡；高風險或高度模糊的任務使用完整格式，中等風險任務可只保留有意義的項目。

若存在合理且低風險的假設，不需要為了確認而停止。只有當不確定性會實質改變結果，或讓執行變得不安全時，才需要先詢問使用者。

若需求存在會影響結果的歧義，agent 應先詢問使用者，不應自行選擇解讀。

完成 preflight 後，除非有阻塞的不確定點，否則可以繼續執行任務。

## 建議輸出格式

### Task Understanding

我理解這次任務是：

- ...

### Known Inputs / Constraints

目前已知的輸入與限制：

- ...

### Assumptions

我目前假設：

- ...

### Unknowns

我目前不確定：

- ...

### Ambiguities

這個任務可能有以下不同解讀：

- 解讀 A：...
- 解讀 B：...

### Risks

可能的風險：

- ...

### Proposed Plan

我建議的處理步驟：

1. ...
2. ...
3. ...

### Files Likely to Be Touched

可能會影響的檔案：

- ...
