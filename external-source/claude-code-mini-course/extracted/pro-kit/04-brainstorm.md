# Codex 版：規劃模式 `/brainstorm`

> 對齊來源：`pro-kit/04-brainstorm.md`
> 原始定位：安裝 Claude Code 的 `/brainstorm` skill，讓 AI 動手前先釐清需求與產出計畫書。
> Codex 改寫定位：建立 Codex 可用的「先規劃、再執行」工作流，必要時寫成 `000_Agent/skills/brainstorm/SKILL.md`。

## 核心意圖

原文要解決的是 AI 直接開做導致方向錯、需求沒釐清、後續返工的問題。Codex 版保留硬性閘門：

> 使用者確認計畫前，不寫 code、不 scaffold、不修改實作檔案、不執行會改變專案狀態的命令。

允許做的事：

- 讀檔
- 搜尋
- 看 repo 結構
- 看 git log
- 寫計畫書

```markdown
# Brainstorm 規劃模式

## 硬性閘門

在使用者確認計畫前，不可以：
- 寫 code
- 建實作檔案
- scaffold 專案
- 執行會改變專案狀態的命令

可以：
- 讀檔
- 搜尋
- 檢查 git log
- 寫計畫書

## 流程

1. 確認溝通模式
2. 確認主題與任務類型
3. 掃描上下文
4. 列出假設
5. 深度釐清
6. 提出方案
7. 產出計畫書
8. 讓使用者決定下一步
```

可選：在 `AGENTS.md` 追加：

```markdown
對於模糊、跨檔、架構、重構、遷移或高風險任務，先使用 `000_Agent/skills/brainstorm/SKILL.md` 的流程產出計畫，再開始實作。
```

## Phase 0：確認溝通模式

先問使用者希望如何討論：

- 小白模式：少術語，講成果、風險、使用者要做什麼。
- 半技術模式：保留必要檔名、套件、API，但附說明。
- 工程師模式：直接講架構、檔案、命令與 trade-off。
- Codex 判斷：預設半技術，依使用者語氣調整。

這個模式要影響：

- 假設列表
- 問題措辭
- 方案比較表
- 計畫書
- 最終是否開始執行的說明

## Phase 1：暖身確認

### 1-1. 確認主題

如果使用者已輸入主題，先回述：

```text
我理解你想做的是：[一句話]。我先確認需求，不會動手改檔。
```

如果沒有主題，問一句：

```text
你想規劃什麼？用一句話描述就好。
```

### 1-2. 任務分類

分類成：

- 新功能 / 新專案
- bug / 問題修復
- 改善 / 優化 / 重構
- 尚不確定，需要釐清

## Phase 2：快速探索

只讀不改：

- `AGENTS.md`
- `000_Agent/CORE_RULES.md`（若存在）
- 專案根目錄檔案
- 相關檔案
- 最近 5 筆 git commit（若是 git repo）

探索結果不要展開成長篇報告，只用來列假設。

## Phase 3：列出假設

格式：

```markdown
根據你的描述和目前專案，我先列出理解：

1. 目標：
2. 使用者 / 使用情境：
3. 本次範圍：
4. 不做的事：
5. 可能風險：

哪些需要修正？
```

小白模式下，把技術詞轉成結果語言。例如：

- 不說「React + localStorage」
- 改說「做成一個網頁，資料先存在你的瀏覽器裡」

## Phase 4：深度釐清

一次只問一題，最多 5 題。

### 新功能 / 新專案

- 給誰用？
- 最重要的 1-2 個功能是什麼？
- 成功標準是什麼？
- 要本機用、網頁用，還是部署給別人？
- 有沒有指定技術或要沿用現有專案？

### bug / 問題修復

- 什麼時候開始？
- 每次都會發生嗎？
- 錯誤訊息是什麼？
- 最近改過什麼？
- 你已經試過什麼？

### 改善 / 優化

- 現在最不滿意哪裡？
- 理想狀態是什麼？
- 改動範圍要多小？
- 有沒有不能破壞的行為？
- 是否需要加測試？

若使用者說「直接做」「你決定」：

- 最多再問一個關鍵問題。
- 然後說明將基於目前理解規劃。

## Phase 5：方案提議

通常提供 2-3 個方案：

```markdown
## 方案比較

|  | 方案 A | 方案 B | 方案 C |
| --- | --- | --- | --- |
| 做法 |  |  |  |
| 優點 |  |  |  |
| 缺點 |  |  |  |
| 風險 |  |  |  |
| 工作量 |  |  |  |

**推薦**：方案 X，因為...
```

若小白模式，欄位改成：

```markdown
|  | 做法 A | 做法 B |
| --- | --- | --- |
| 做完長什麼樣 |  |  |
| 好處 |  |  |
| 壞處 |  |  |
| 可能風險 |  |  |
| 未來可延伸 |  |  |
| 需要你做的事 |  |  |
```

如果只有一個合理方案，也要明確說：

```text
這個任務比較直接，我建議只採一個方案：[說明]。你確認後我再寫計畫。
```

## Phase 6：產出計畫書

儲存：

```text
100_Todo/plans/YYYY-MM-DD-[topic].md
```

模板：

```markdown
# [計畫名稱]

> 建立時間：YYYY-MM-DD HH:MM
> 類型：[新功能 / 問題修復 / 改善優化]
> 狀態：待執行

## 一句話目標

## 背景與動機

## 已確認假設

## 選定方案

## 具體步驟

### Step 1：[名稱]

- 做什麼：
- 產出：
- 注意：

## 不包含在本次範圍

## 風險與處理方式

## 驗證方式

## 執行後回報格式
```

### Self-review

寫完後檢查：

- 沒有 TBD、待確認、之後再說。
- 步驟互相一致。
- 步驟不超過 8 個；太大就拆計畫。
- 每一步具體到 Codex 能執行。
- 驗證方式不是空話，例如「跑測試」「截圖確認」「檢查輸出檔」。

## Phase 7：下一步

問使用者：

- 現在依計畫執行
- 先修改計畫
- 先存著

只有選擇「執行」後，Codex 才開始修改檔案。

## Guardrails

- 不跳步，但可縮短。
- 不因任務看似簡單就直接寫 code。
- 不一次問多個問題。
- 不空泛稱讚，直接推進釐清。
- 挑戰範圍膨脹。
- 遵守 YAGNI，只做現在需要的。
- 全程對使用者用繁體中文；程式碼與指令保持原文。

## 完成檢查

- `000_Agent/skills/brainstorm/SKILL.md` 存在
- `100_Todo/plans/` 或 `plans/` 存在
- 若已生成計畫書，檔名符合日期與主題
- 計畫書沒有 placeholder
- 實作前已得到使用者確認
